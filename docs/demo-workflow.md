# Demo workflow

2026-10-23 最终规则：VLA后无论当前Decisions能否确认黑件，双臂都必须回固定观测位姿。当前位置确认黑件时，先用同次RGBD分割测量黑件并加入保留背景场景（头部优先，深度不足依次尝试左/右腕）；未确认时不建立黑件，移除过时活动粉件层后回位。回位后重新采三RGBD、联合Decisions确认并分析全部当前清单实体，再重建全局2cm TSDF/ESDF；首次桌面cuboid继续复用。所有粉/黑抓取前都在观测位姿，禁止VLA位姿直接抓取。最后黑件入盒确认后也必须沿最新场景回初始位姿，成功回位才完成任务。



See the [current skill guide](luna-skills-guide.md) and [DemoProgram](../src/luna_mujoco/demo_program.py). Responses receives actual skill contracts, three observation-pose RGB images and the user instruction once, producing a bounded program with both executing arms for each selected pink input. The executor validates each skill against live facts. Before execution, bind_inventory orders confirmed sources by measured horizontal distance to the fixed robot base, nearest first; count mode selects the nearest N. This geometry policy is independent of object color and shape. Permanent IDs and image labels remain unchanged, and each selected input finishes its whole process before the next input. The initial RGBD order is frozen for the run and archived separately from identity.

Each process runs in order: left-arm pink grasp → shared table-region center → Decisions placement confirmation → dual-arm natural preparation → explicit MuJoCo VLA mock → Decisions at the current natural arm pose → new black entity ID → dual observation pose → pre-grasp Decisions and a new RGBD remap → right-arm black grasp → attached ordinary plan_pose above the right bin → open/drop → Decisions confirmation. Only that last confirmation completes the process. The next process cannot start earlier. VLA itself remains a mock.

Original pink IDs and initial left-wrist display numbers remain fixed, including count-excluded inputs. A process record links input_entity_id and output_entity_id as provenance, without claiming visual proof that different appearances have the same identity. The source ledger retains its completed stage0 as consumed; the new product starts stage1. Geometry, grasp, attachment and drop use that product ID. The UI shows all entities, pending unpack inputs, active processes and completed processes; completion counts processes once.

These lists are views of one entity/process ledger, rather than three separately edited inventories. The immutable initial observation remains the reference for original entities; the live ledger also retains consumed pink inputs and adds independently identified black products. `pending_unpack_ids` contains inputs whose process has not started, while a pink input already on the table is represented by its active process. `product_entities` contains all confirmed unpacked outputs, including products still on the table, being transported, and completed in the right bin. A confirmed unpacked product is therefore not equivalent to a completed process. Repeating the same confirmed creation evidence returns its existing product ID rather than counting another product.

A CURRENT-only Decisions request confirms current roles. Remaining pink candidates additionally receive INITIAL/CURRENT comparison with choices from their original IDs. All remaining pinks require camera2 coverage and a unique accepted identity at confidence ≥0.8; unknown or conflicting assignments stop. The initial reference is never rewritten. Completed black products retain their independent records; current right-bin occupancy is an explicit collection with those IDs as members, not claimed individual reidentification.

Only the actual dual observation pose can rebuild the latest inventory-only 2cm TSDF/ESDF. First-observation table cuboids are cached. Current cleaned RGBD registers the known blue CAD shape without simulator poses; each box contributes 49 separately declared convex collision meshes preserving the cavity, alongside the measured voxels. Missing or ambiguous plane evidence stops. All other movement uses the retained scene. Action-derived occupancy is labeled separately and is not new RGBD measurement.

GraspGen uses current segmented geometry, arm-specific tool conversion and one +1cm insertion along tool Z, then the downward45°/away-from-robot filters before batched IK and plan_grasp_batch. Lift success uses gripper position feedback. Attachment has24 spheres by default, at most31, and intentional overlap with all nine same-hand gripper links. World, upstream, camera and other-arm checks remain. Shared collision clearance is10mm; loose table-center placement preserves the grasp orientation. Attached plan_pose above the right box preserves lift orientation and advanced quintic/time-scale settings.

verify_unpack captures fresh RGB at the current post-VLA pose and validates the confirmed table-release BEFORE capture as process evidence. It neither moves the arms nor maps. Its verification_capture summary binds capture time and all three image hashes; the product reference retains those RGB images. The later observation-pose capture is distinct and must pass the ordered cross-frame evidence check before the second grasp. Both grasp stages require live dual observation pose and a scene built from that same observation. Decisions runs at each pre-grasp observation, not for individual GraspGen candidates. Decisions sees the current three original RGB images plus head detail. Each camera answers result and conflict: one view must show a separate black tabletop product and no distinct competing tabletop product, both confidence≥0.8; any credible conflict vetoes. Other unclear views do not veto a clear supporting view. Only this confirmation creates product-*. Robot parts, pink objects and objects inside boxes are excluded from competition. Historical same_item answers cannot satisfy the six-question schema.

Drop verification archives BEFORE/CURRENT original RGB and box details. Both black-in-bin and at-least-N+1 distinguishable current black products must be yes with confidence≥0.8. Existing N products alone cannot confirm the current release. The validated holding/transport/open feedback chain identifies the active product; counts never reassign old IDs. Unknown visibility stops, and neither counting nor mock receipts prove hidden contents absent.

For the second output, its new identity is grounded in the single active second process and a currently confirmed, noncompeting tabletop black product, after the first process has been confirmed complete. The subsequent current-role check also requires visible occupancy for the previously completed right-bin products. This is process-based association in the controlled sequential task, not visual proof from a UUID or a unique surface mark. Unexpected relocation or occlusion of existing products can make the association ambiguous; prior completion and a new tabletop detection alone do not prove an object's physical history.
