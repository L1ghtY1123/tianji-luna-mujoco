# 2026-10-19 执行耗时核查与修正

用户参数保持 time_scale=3，七项阶段停留均为1秒。使用用户已确认场景，任务为“抓取盒子中的绿色和红色物体，放到桌面黄色区域”。本轮不改变物体身份算法、JEV技能选择、观测时机、放置约束或碰撞阈值，不修改SDK/vendor。

## 修改

1. 停留使用单调实际时钟。原实现等待1秒仿真时间，仿真低于实时速度时会拉长实际停留；输出另列simulation_duration_s。
2. 物理循环只执行原有mj_step；删除每1ms额外的mj_fwdPosition，改为在受锁保护的机器人/场景快照读取前刷新。原控制器只消费关节状态；RGBD渲染使用独立数据副本并自行forward。保持1ms积分、实际接触与控制参数。
3. WebSocket只复制新增事件，前端无新事件时不重新渲染完整执行记录；HTTP完整记录保持不变。
4. attachment准备与同一次静止放置规划共用实测快照，防止夹爪反馈微小变化立刻销毁刚初始化的持物IK模型。执行前、松爪前仍使用独立最新反馈做原有检查。

MuJoCo接口依据为项目锁定3.10.0版本的[官方API文档](https://mujoco.readthedocs.io/en/3.10.0/APIreference/APIfunctions.html)。cuRobo源码锁定8e734f3ced1df898990bcd92de40abce475907db；本轮不修改其API、批量算法或内部缓存限制。

## 放置与建图的具体开销

无归档复测的第二次plan_place共47.39秒。放置批次调用19.17秒，其中backend初始化12.02秒、scene/peer更新0.16秒、求解和验证6.97秒。之后空爪撤离规划器初始化又用了10.94秒。两次放置均为18/18通过IK，当前批已有可行解，选中了yaw=0的候选；不是18个yaw反复失败，也不是attachment二维投影限制。

服务日志还显示每次prepare_attachment与紧接的IK各建立一次容量100模型。调用链证实两者使用了不同时间读取的实际夹爪反馈，而反馈是模型缓存键的一部分；修改4让同次规划共用快照，消除这一重复。其他模型初始化及完整命令复核仍有开销，不声称已经全部优化。

无归档复测第二次build_scene共10.89秒，其中双臂观测运动阶段8.38秒（实际运动4.90秒）、到位采集及感知1.94秒、实例建图0.56秒。此前放置后的原位观测2.81秒、全障碍物建图3.44秒。两次地图的用途不同：原位地图保护返回观测位姿，到位后的地图用于下一次抓取与放置。保持用户要求的两阶段时序，没有为了减少建图次数使用缺少已放物体的旧地图。

显存余量不是当前唯一约束。IK容量100、轨迹批16保持原值；这一轮没有在缺少同场景对照数据时扩大batch，也没有减少18个yaw、碰撞采样或精细盒底地图。可继续测量模型初始化及GPU资源争用，但本记录不把未经验证的显存调整写成提速结果。
