# cuRobo 调用与各阶段碰撞模型审计

本轮核对官方源码、生产构造链、公开规划调用、夹爪/attachment状态及检查与缓存生命周期。结论：SDK原文件一致，但项目封装此前不止增加高级设置和插值，曾有状态传递及重复计算缺陷。不能继续使用“整个项目与官方完全一致”的表述。

## 已修正

1. 抓取IK和`plan_grasp_batch`漏传两侧夹爪开度，检查器的`fixed_open`还将对侧手也设为全开。现在请求必须提供两侧实测值，只覆盖执行手为全开。普通pose/place入口也不再接受缺失反馈后默认全开的输入。
2. 官方抓取三段在开爪模型下规划，闭爪后几何改变。保留官方lift轨迹，以实测闭合模型检查后执行；此时无attachment，lift完成、夹爪核验后才附物。
3. 原始轨迹返回后、插值前的单臂重复整段检查已从生产调用删除。最终五次插值命令仍检查10mm净距。执行阶段只复用完整请求哈希一致的结果，不能将不同起点连接、对侧手、夹爪、附件或场景的证明混用。
4. 普通place无解不再销毁已预热的compound求解器。SDK异常仍清理异常实例。

## 官方边界

锁定提交`8e734f3ced1df898990bcd92de40abce475907db`。重新比对运行容器788个官方文件，changed为空；仅缺不参与算法的`examples/README.rst`。范围包括Python、CUDA/C++、配置及资产。SDK及vendor均未修改。

抓取调用官方`BatchMotionPlanner.plan_grasp`；place前两段调用官方`MotionPlanner.plan_grasp(plan_grasp_to_lift=False)`，释放后的lift以公开`ToolPoseCriteria.linear_motion`和`plan_pose`规划；普通运输使用公开`plan_pose`。项目未替换这些调用的内部优化器、IK或重试循环。官方`plan_grasp`不公开所有普通pose的高级参数，因此不能通过私有覆盖强行注入。

额外的10mm硬净距筛选、目标高度计算、物体层开关和持物管理是项目逻辑，不是官方示例。双臂最终命令仍存在服务端及客户端验证；vendor历史单目标grasp方法尚有失败时清缓存行为，但本服务没有注册对应HTTP入口。详见[逐入口审计](../curobo-public-api-audit.md)。
