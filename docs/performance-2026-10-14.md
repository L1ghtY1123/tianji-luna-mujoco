# 2026-10-14 场景与规划耗时核查

测试环境：固定 cuRobo SDK `8e734f3`、Ubuntu RTX PRO 6000 Blackwell、独立进程；所有 GPU 探针只调用建图和规划接口，不发送机械臂命令。真实 RGBD 采用已保存的三相机观测；规划吞吐探针使用明确标记的合成可达目标。完整探针、原始 JSON 和日志保存在本地忽略目录 `data/cumotion-investigation-20261014/`。

## 结论与选择

- 抓取批次保持 **16**。相同可达位姿的合成目标、热态每批 8/16/32 个分别为约 **0.56/0.95/1.83 秒**。32 个的总吞吐略好，但一个批次已成功时等待更长；这组数据不能证明实际场景中增大批次会更快。真实任务还含 GraspGen、独立 batched IK、轨迹规划和实际命令检查。
- 放置的 72 个 yaw 每隔 5°，先固定一个位置，再按 **8 个一批**调用 cuRobo。没有单独对 72 个方向预做 batched IK。SDK `plan_grasp` 在每批内部先做目标集预规划（含 IK 与轨迹优化），再做 approach 和 place；项目随后单独规划已松爪的 retreat。此实现直接复用同一个已装载物体的 batch 规划器。
- 热态持物 place 合成探针约 **0.45 秒/8 个**，首次约 **5.44 秒**，其中目标集预规划约 **4.24 秒**。此差距主要来自首次图录制和初始化；具体实物的可行率与耗时仍需在真实任务中记录。
- 真实三相机 RGBD 重复建图，对照原代码热态 **1.15/0.87 秒**，当前 **0.59/0.39 秒**；各相机有效深度点分别保持 **183887/181107/229712**，没有删点。首次建图两版约 **5.08/4.77 秒**，包含初始化，不能用来推断稳态收益。
- 当前建图返回 `service_timings_ms`、`segmenter_timings_ms`、`timings_ms` 和点云预处理细分计时。热态第三次：服务总约 391 毫秒，其中深度准备约 53、Mapper 约 190、自由空间证据整理约 114 毫秒；Mapper 中融合/ESDF 约 6 毫秒。各时间是顺序墙钟区间；GPU 同步可能被后续区间承担，不把它解释为独立 CUDA 内核耗时。
- 已知双臂观测关节目标直接走公开 `plan_cspace`，避免 FK→TCP pose→IK。合成双臂任务热态约 **0.11 秒**；真实障碍物路径仍须由当前场景碰撞验证。使用最新夹爪反馈验证轨迹时复用已缓存世界，合成探针约 **0.38 秒**，并正确拒绝新障碍物。

上述优化只影响 skill 请求中的建图和规划。场景体素仍为 **1 cm**，没有持续更新地图。不同任务、障碍布局、冷态和 GPU 共用负载会改变绝对耗时；下一次真实任务应按新增计时和 replay 记录重新比较总流程。
