### 为什么较快

- ESDF 使用已知物体几何，每次对桌面及三个物体计算解析有符号距离，建立四层 1 cm 体素并上传 GPU。没有相机、分割、深度融合，也没有复用一份旧 ESDF 冒充重建。
- 缓存的是形状/尺寸对应的 4096 点局部表面点云，以及服务中的已加载模型、求解器实例和 CUDA Graph 等资源。当前 GraspGen 接口每次重新调用官方 `run_graspmoe`。
- Docker 原始服务日志进一步确认：黑块在 `07:06:44 UTC` 完成扩散采样和 OBB 分支，最终 100 个候选为 77 个 diffusion + 23 个 OBB；蓝柱在 `07:10:37 UTC` 为 60 + 40。两次都不是读取旧的候选结果。
- 两次分别向 cuRobo 发出一次 `/geometry/build`、两次 `/tools/solve_ik_batch`、一次 `/tools/plan_grasp`。每臂批量 IK 输入 100 个候选，A、B 两次请求顺序执行。
- 完整轨迹规划是选臂后按分数顺序逐候选尝试，成功即返回，并未给两臂各 100 个候选全部规划轨迹。上述两次均首个有效候选规划成功，`prior_failures=[]`。
- cuRobo 的启动配置是 `warmup=False`，求解器延迟构建并缓存。蓝柱第二个 IK 请求日志出现两次 CUDA Graph 录制；黑块对应时间窗口没有。这是耗时变化的直接证据，现有计时不足以把整个差额精确归因于录图。

这些是服务已运行一段时间后的样本，不代表冷启动时间或普遍成功率。

## JEV 的真实顺序

先选择任务和物体属性，然后循环：读取当前仿真状态及 facts → 把全部已注册 skill 的契约与 `SKILL.md` 交给 JEV → JEV 从全部 skills 和 `stop` 中选择 → 程序检查所选 skill 的执行条件 → 条件满足才执行并等待返回 → 写入真实产物 → 再读取状态并调用 JEV。

Python 不在作答前筛掉 skill，也不提供 `eligible`、`unmet` 等计算结果。条件不满足时记录拒绝事件和原因并结束任务，不执行、不自动重试、不替换 JEV 的选择；`stop` 也结束任务。程序提供 question 及完整 skill 选项，JEV 根据每轮实际 state 和技能资料判断顺序。

Registry 在启动或后端重载时从 `skills/` 目录发现有效的 `contract.json` 和 `SKILL.md`。这只让新 skill 进入决策目录；它仍需要对应的 Python 执行实现、输入/输出产物、`requires`/`provides` 契约及测试，说明文件不会自行实现算法。

例如黑块这轮实际是：观察、识别目标、建 ESDF、生成抓取、评估两臂、选臂、规划、执行、验证。每个技能前有 JEV 选择；识别目标与选臂技能内部另有一次对应的 JEV 判断。属性的三个问题同属一次请求，不是提前规划全部技能。

真正开始机械运动之前，`plan_grasp` 已返回完整 approach/grasp/lift。`execute_grasp` 内连续开夹爪、接近、抓取、闭合、记录参考位姿、提升，中间不调用 JEV；完成后 JEV 再选择 `verify_grasp`。所以当前是技能之间的闭环决策，不是每个关节控制周期都问 JEV。

## 双臂位姿与选臂的实际依据

点云及原始候选在物体局部坐标系；兼容接口中的 `camera` 名字不表示本项目存在相机。对每个原始候选分别计算：

```text
T_world_tcp_arm = T_world_object @ T_object_grasp @ Rz(theta_arm)
                  @ Tz(0.195 m) @ Tz(-0.185 m)
theta_A = 180 degrees
theta_B = 0 degrees
```

A 的 X/Y 两轴一起取反，Z 接近方向保留；两臂的目标 TCP 矩阵不同。这个 180° 沿用原 `tianji_base` 的双臂抓取姿态约定，原注释说明其用途是让位于工具 ±Y 两侧的左右腕相机处在抓取同一侧。它不是左右机械臂肩部基座变换的替代。

cuRobo 共同根为 `Link_Base`，两臂求解目标分别为 `TCP_Link_L/R`。左右基座的固定位置和旋转由各自 URDF 链处理，不再把共同世界坐标误当作各自肩部坐标。对保存的 63 个成功 IK 重新依据 URDF 做 FK，目标都与上述公式一致。候选 #78 中两臂位置相同，A 旋转为 diag(-1,+1,-1)，B 为 diag(+1,-1,-1)；FK 位置残差分别约 1.14e-7 m、2.04e-7 m。

工具偏移 185 mm 是复制的默认配置，未在本次重新标定。原项目支持每臂完整工具变换，新项目当前固定使用纯 Z 偏移；这一点不能推广为任意工具安装都适用。

选臂的实际输入包括当前关节、每臂 IK 可达结果、GraspGen 分数、候选关节角和 IK 位姿残差。没有可达候选的臂不进入选项，JEV 可选择 `none`。

|---|---:|---:|---|
| 黑色方块 | 39 / 100 | 34 / 100 | A |
| 蓝色圆柱 | 1 / 100 | 2 / 100 | B |

这是提供给模型的证据和它的实际输出，不是对其内部判断理由的推测。目前存在三项明确限制：

1. `public_summary` 会把超过 8 个候选缩成总数和前三个详细项，JEV 不能逐个比较全部可达候选。
2. 提示词写了“关节距离”，但代码未显式计算该指标，只给当前与候选关节角，不能声称已按最小关节移动量择优。
3. 选臂前只做 IK，不比较两臂完整三段路径的时长、长度或最小净空。IK 可达不保证完整路径可行；所选臂全部候选规划失败时，当前会失败，不自动切到另一臂。
