# 每个 JEV skill 的契约要求

规范适用于算法、运动执行、验证及状态绑定 skills。状态绑定也是固定流程，例如“校验 JEV 选中的实例 → 绑定实例”；不要求每个 skill 都引入新的算法库。

## 必须说明的内容

| 项目 | 必须回答的问题 |
|---|---|
| 目的与边界 | 一次调用解决哪个问题？什么明确不属于它？ |
| 调用条件 | 哪些观测到的事实或证据缺口支持 JEV 选择它？这些是选择依据，不是程序自动跳转表。 |
| 输入 | 类型、单位、坐标系、实例/动作/帧/场景标识、配置版本；每个可选值有明确语义。 |
| 硬前提 | 哪些条件由程序检查？不满足时在什么副作用发生前拒绝？ |
| 固定算法 | 有序步骤、允许的有限分支、候选生成与排序、退出规则；不得含“让 JEV 自由调整直到成功”。 |
| 输出证据 | 本次实际测得或计算了什么？结论适用范围是什么？不能只写 success。 |
| 状态与副作用 | 是否拍照、移动、开闭爪、更新身份、建图、调用 API；哪些旧结果失效？ |
| 失败与未知 | 输入拒绝、证据不足、算法无解、服务错误、取消和超时如何区分？哪些部分已经执行？ |
| 预算与复用 | 每次采集/模型调用/候选/执行/耗时的上限来自哪里？缓存键包含哪些实际输入？ |
| 验证依据 | 正常、缺失、冲突、过期、取消及错误场景；当前实现的限制。 |
| 实现状态 | 定义、已接入、已测或已部署；不能互相替代。 |

`contract.json` 是运行时接口的一部分。现有 schema 不支持的字段先放入文档，若要扩展 schema，必须同时更新生产者、消费者和测试，不能只把字段写进去。精简目录至少让 JEV 知道目的、输入、前提、主要输出和关键限制。

## 结果语义

返回值名称可沿用项目现有约定，但必须明确映射以下区别：

- 流程完成：不自动代表抓取、放置或任务已成功。
- 证据不足：说明缺失或冲突，保留 unknown，不增加虚假的动作失败次数。
- 有限候选无解：说明检查过哪些候选和哪些约束，不能声称整个空间无解。
- 契约拒绝：说明未满足的前提，不执行替代动作。
- 服务错误、取消、超时或预算耗尽：报告已执行阶段及资源状态，丢弃不能再应用的迟到结果。

动作是否成功由验证证据支持；任务是否完成、失败后重试/补看/暂缓/结束由 JEV 判断。程序可以立即阻止非法动作或执行取消，不把这解释为替 JEV 选择恢复策略。

## 固定算法与任务策略

允许：“按评分稳定排序，分有限批次求解，首个有完整可行解的批次内按已声明规则选解。”

不允许：“失败后自动移动去观察，再重试三次，最后换臂。”后者包含任务策略；只有用户明确授权该固定业务流程时，才能作为另外声明的能力讨论。

执行 skill 可以把末次 RGBD 采集作为固定后置步骤，必须在契约中写明并返回可复用的 capture。分析 skill 可以在同一帧内按有限相机顺序处理，不应因此被计作多次传感器采集。

## 证据和版本

- 观测标识、仿真/机器人会话、捕获时反馈与标定必须绑定。分析和场景还要绑定参数版本与输入指纹。
- 历史点云可用于身份关联或声明过的持物几何参考；不能作为当前相机新看到的点。
- 桌面平面外推、持物刚体预测等必须标为推导，并记录适用假设。
- 相关环境改变时旧地图应标为待更新；纯视觉语义补充不能伪装成新几何观测。只有新建图成功才能更新对应地图身份。
- 选择目标变更后必须重算该目标相关的证据，不能用其他目标的相机可见性阻塞或放行它。

## 验证与维护

先从 registry 确认实际可调用项，再逐项核对执行路径；不得用空目录计数。至少演练：另一只腕部相机提供执行臂所需信息、同帧重复分析、未知结果、指定臂无解、过期计划、部分执行后报错。阈值必须有配置和验证依据，不创造“看到几面/多少点就绝对安全”的通用数字。

对旧 skill 的审查可以报告差异；只有对应行为和契约修正并验证后才标为符合。不能通过把未来规则写入 SKILL.md 来掩盖仍然不同的执行行为。
