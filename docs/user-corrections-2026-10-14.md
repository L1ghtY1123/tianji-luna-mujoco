# 放置验证、计算接口与部署修正

本文件记录较早一轮处理。后续用户将放置验收改为夹爪释放标准，并进一步核实基础镜像已包含Open3D；当前结论见[后续修正](release-and-gpu-review-2026-10-14.md)。下文的视觉回放及0.3镜像说明是当时记录，不覆盖后续修正。

放置验证失败与计算失败必须分开。实验 `3d70ff079017496aadcb76a72dc55e5a` 已执行放置，但 SAM3 未将绿色目标关联回原 ID，验证返回 unknown；随后三相机关联明细令 JEV 输入预算超限，未进入视觉辅助决策。修正后的决策摘要保留每相机状态、缺失 ID、相关未关联记录、夹爪状态及原始日志引用，完整关联表仍留在实验日志。同一记录的估算输入由 24,386 降为 20,452（新提示词前），不提高 24,000 的预算上限。

JEV 在纯视觉放置验证 unknown 且同帧尚未分析时优先选择已有 `inspect_visual_result`，再选择 `verify_place` 消费图像判断。没有新增视觉 skill，也没有在验证函数中写自动恢复。看不清、HTTP 429 等仍返回 unknown。视觉 API 凭据只读取原有受保护配置；本次提供的密钥与已有配置一致。使用原实验 RGB 相机录像做一次独立视觉请求，返回 confirmed，耗时约 21 秒；它不改写历史任务状态，也不构成新一次物理搬运验收。

同一历史状态另做了一次真实JEV决策回放：新请求估算20,879 tokens，约1.2秒返回 `inspect_visual_result`。该回放只验证决策，没有驱动机械臂。图像请求与JEV决策回放分别成功，尚未用新代码跑完整抓放实验。

最新实验 `9bde475885b74b8ebee296686f542a1f` 的 72 个放置 yaw 均通过 IK，随后轨迹优化触发 CUDA 显存不足，尚未执行 place。原 HTTP 边界把该异常包装成通用失败。本次保留异常原因链，返回 HTTP 503 / `CUROBO_CUDA_OUT_OF_MEMORY`，结论明确说明计算未完成，不能据此判断不可达或碰撞无解。

抓取和放置共用 `/tools/solve_ik_batch` 及同一个 SDK 求解算法，容量固定为 100；不足 100 个的末批重复末候选，返回时去除填充项。200 个抓姿为两批，72 个 yaw 为一批。放置使用实测闭爪配置与 attachment，抓取使用原张开配置，不能错误共享不同机器人配置的 CUDA graph。`plan_grasp_batch` / `plan_place_batch` 是后端接口名，不在 JEV skill 目录；两者都调用同一公开 SDK `plan_grasp` 算法。高层 `plan_grasp` 与 `plan_place` 保留不同的执行前提和阶段合同，日志按抓取/放置显示。轨迹批容量与 IK 容量独立，当前分别保留 16 / 8；不因 IK 设为 100 就把轨迹批也设为 100。

`jodell-curobo:0.3.0-visible-cloud-guangyu` 创建于 10 月 9 日，是 `0.2.0-guangyu` 加入 Open3D 0.19 的派生镜像，SDK commit 保持 `8e734f3ced1df898990bcd92de40abce475907db`。本次及上一轮修改没有构建镜像。两镜像共享原层，派生层仍有额外磁盘成本。启动脚本现禁止自动构建，Compose `up` 显式使用 `--no-build`。既有镜像不作未经确认的删除。

上一轮网页 500 是维护时直接重建容器、未保留 UID/GID 导致：Compose 默认 1000:1000，而挂载 `.env` 只允许 1003:1004 读取。原页面无此故障。应使用保留当前用户的启动器；普通源码更新使用源代码挂载与 Uvicorn/Vite 重载，不重建网页容器。后端 worker 重载仍会清除内存仿真状态，所以更新前保存实验及状态。GPU 服务未启用源码重载，修改其后端或模型后仅重新启动该服务，不构建镜像。

本次同步采用Git快进，网页容器保持原实例，后端源码自动重载；已有cuRobo容器停止后原样启动，未重建。维护前状态存入 `data/user-corrections-20261014/pre-update-state.json`。GPU显存不足是共享资源问题，本次补全了报告，不能宣称已消除资源不足。碰撞球8轮重新拟合的候选均未达到替换条件，继续使用309球；详见[拟合记录](collision-refit-2026-10-14.md)。
