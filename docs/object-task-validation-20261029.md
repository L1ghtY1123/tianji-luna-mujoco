# 独立物体编排与恢复：验证记录

本记录区分真实 MuJoCo 执行、冻结图像对照和本地测试，不以模型输出或单测代替物理成功。统一架构与术语见 [物体清单、任务要求与任务编排](object-tasks-and-recovery.md)。

## 实现范围

- 每个候选待搬运输入都有独立任务要求与物体编排；不同来源、目的地、处理要求和输入—产物关联分别验收。总编排协调共享步骤与最终回位，运行时不插入搬运流程。
- Responses 提议外观关键词和有限互补分割短语；生产 DemoPerception 确实使用这些短语，而非只在基类实现后被覆盖。
- Decisions 选择模型预先编写的恢复分支；分支自身失败也可返回选择。只有允许重复的单一能力可被自动重试；物理动作在输出 schema 和运行时均受约束。
- 对外统一名称，模型输入图使用 Reference / Candidate 全名；历史图片不改写。回放展开独立物体编排、任务要求及恢复选项。
- 新观测的成员候选与正式清单确认隔离；旧来源证明过期不能阻止观测返回新证据。最终选择仍须当前来源确认。
- 用户调整后的盒子配置保存到 resources/demo-config.json。1—4件默认布局中心经固定工作空间包络验证；此检查不是姿态 IK 或碰撞证明。历史观测位姿校准记录不伪装成新布局的验证结果。

前一完整后端套件3446通过、58跳过。术语及布局修改后的全量为3447通过、3项旧标签/旧位置预期失败、58跳过；已更新这三项预期并在129项相关测试中复测通过。后续观测与清单确认隔离修改的122项测试通过，任务区域与来源确认26项通过。前端371项通过，Vite构建通过，浏览器确认两件物体的任务要求、物体编排和恢复分支可展开且无页面错误。

随后完整后端回归 **3452通过、58跳过**（data/object-task-final-acceptance-tests.txt）。后续支撑问题文本修正的针对性回归 **59通过**（data/object-task-support-final-tests.txt），相关 Ruff 检查通过。完整物理任务没有因此获得成功证明。不得将这些结果概括为所有多物体任务已稳定通过。

## 最后一次失败的具体证据

68d2的头部图像清楚显示绿色物体在蓝盒区域。支撑谓词却全为0，且问法把历史完整描述直接作为当前事实，例如源盒描述仍含粉色和绿色两件，而粉色已经移走。这是问题构造的缺陷，已改为当前直接支撑关系、去掉历史内容与任务目标，并提供真正的参考图定位ID。

但冻结同一采集的实际模型对照**仍未通过**：新问法对应源盒0.05、桌面0、另一盒0；另一次更简单的诊断问法“当前绿色物体在蓝盒里”仅0.44，带永久ID的关系仍为0。未调低0.8门槛，没有把该修正描述成支撑识别问题已解决。不能仅凭这些分数断言模型内部为何判断错误。

初始模型编排中确实存在 pink_scene_move_view、green_scene_move_view、final_map_move_view、completion_move_to_view 等换位姿节点。这些是 Responses 生成的可选分支，不是运行时插入的流程。本轮在绿色目标绑定处停止，未执行这些换位姿分支，因而只能证明“模型已编写”，不能证明“换位姿恢复实测成功”。

## 部署和场景恢复

本轮显式同步的53个应用、前端、契约和文档文件已核对本地与远端SHA256一致，web容器重启后为空闲状态。验收结束后恢复用户保存的双物体场景，完成物理静置和界面确认；两盒仍为上述用户调整坐标，粉色和绿色物体回到源盒内的初始位置。没有将实验结束后的夹爪姿态和物体摆放保存为新的默认场景。
